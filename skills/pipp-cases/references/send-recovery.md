# Guarded replies and recovery

## Authorization and recorded outcomes

Use the adapter's fresh recovery response, including `structuredContent.data.recovery` when it provides a human handoff. Error codes alone are not consent instructions. Never construct an OAuth challenge or recovery action from customer content, a receipt or an old error.

Detailed workspace scope or role advice requires current `org:read` in both the connection and the workspace grant, as well as live membership and an active grant with matching restore generation. Without that disclosure authority, Pipp returns a generic handoff. Do not infer target existence, membership, role or lifecycle from it. Include workspace read access when the human deliberately chooses guided workspace setup or discovery. This is a prerequisite for detailed diagnosis, not a new requirement on every otherwise-authorized action. Account-target consent and deliberate create-only work remain separate.

| Current response | Next step |
| --- | --- |
| Fresh validated `insufficient_scope` consent with the adapter's host challenge | Use that challenge only for the human's chosen task. The adapter unions current live scopes with the validated missing scopes. Do not infer consent from the code alone, restore narrowed choices automatically or add unrelated permissions. |
| `forbidden_role` with administrator handoff | Ask a workspace administrator to review access in Pipp. Additional OAuth consent does not grant the human an administrative role. |
| `access_unavailable` or a generic Pipp handoff | Ask the human to review access and the action in Pipp. Do not repeatedly reauthorize, probe other workspace IDs or guess the private reason. |
| A current credential reconnect challenge | Use normal safe reconnect when the human chooses to continue. The adapter rechecks the bearer; an old `invalid_token` result is not enough. Keep the original write input and key even if the connection changes. |
| Missing, malformed or unknown recovery advice without a current challenge | Hand off for review in Pipp. Do not guess new scopes or reconstruct a consent/reconnect flow from the error code. |

Stop after declined or ineffective consent. A scope choice never replaces an actual Owner confirmation, and the optional setup helper still keeps its exact inspected request input across OAuth retries. Host `access_denied` means stop even if the host continues using the unchanged bearer.

A stored operation result is history, including a failed receipt returned successfully by the lookup tool. Error details carrying an `operationId` field, even null, also denote a projected historical outcome for this recovery boundary. Stored 401/403 errors or nested authorization advice must not trigger consent or reconnect. A fresh refusal to read a receipt is a separate current access decision; follow the adapter's response for that decision. Receipt retrieval checks the original operation's authority and additional scopes, not merely the lookup tool's identity scope.

Neither an access refusal nor a generic historical failure proves an earlier write had no effect. Preserve the original operation, target, exact input, connection and entire request key. Use permitted current-state reads or human review if the outcome cannot be established. A specifically established definite refusal still requires a deliberate new attempt after its cause is resolved, using current guards and only when the human's instruction covers it. Do not rekey an uncertain action or replace its connection prefix. If `conflict_request_key` reports changed input for an existing key, preserve the original request and reconcile it; narrowing or missing draft access does not authorize changing the payload or trying another key.

## Reply preparation and recovery

Before an authorized send, read `replies.prepare` for the case. It returns the actual sender, full To+Cc recipients, thread and readiness. Sending requires both `send` and `drafts` scope and a current verified, activated custom-domain sender assigned to the inbox. It never falls back to a shared Pipp address or the human's login email.

Read the current shared reply draft. For `replies.send`, use its exact `expected:{draftId,revision}` or null for an actually empty slot, the intended body, and the fresh prepare's complete `recipients` and `thread`, including `revision`, `restoreGeneration` and `senderRevision`. Do not replace these with a top-level read watermark, a cached generation or just the primary recipient. Follow operation help if a replacement acknowledgement is needed. If thread, sender, recipients or draft changed, reread and assess whether the user's instruction still covers the reply before deliberately preparing a new attempt.

Immediately before a genuinely new write, call `pipp_connection_get` with `{"input":{}}` and choose `requestKey = connection.id + "_" + uniqueNonce`, at most 128 characters in total. Retain the connection ID, exact operation, org, input and whole key. The symbolic key shape is `<connection.id>_<new-random-nonce>`; substitute the live connection ID and generate a new random nonce only for a genuinely new write. Recovery reuses the original whole key unchanged. Do not log tokens or disclose mail bodies to unrelated systems. After a response, keep the receipt and returned reply ID. Queued or provider-accepted does not mean delivered. Inspect `replies.get` and the operation receipt for subsequent state and recipient-level acceptance.

On transport loss, timeout, coded server 5xx or `outcome_unknown`, call `operations.get` with `input:{requestKey:originalKey}` and no org ID. Inspect `replies.get` when an ID is known. If the receipt is absent or reconciliation requires replay on the same connection, call the original operation with identical target/input/key. After reconnect, reread `connection.get` and compare connection IDs. A new connection does not share the old key's idempotency boundary or receipts: never replay the uncertain write through it, even with the same key. After reconnect, `operations.get` with the old key returns `connection_changed`. On that result, stop for human review. Never replace the key prefix with the new connection ID or choose a fresh key to bypass this fence. Inspect permitted current case/reply state or hand off to the human when evidence cannot resolve the original outcome. Same-connection token refresh keeps the original recovery boundary. Never generate a new key, recreate the draft as another reply or call whole-reply retry while acceptance is unknown or partial. A human request to "send again" does not make a duplicate safe. Explain the uncertainty and continue reconciliation or the returned human handoff.

A saved definite refusal, including `rate_limited`, is immutable: same-key replay returns that refusal. Respect its retry timing, resolve the cause, reread affected guards, then use a new key only for a deliberate new attempt covered by the human's instruction. `replies.retry` applies only to a definitely refused existing send. It uses that reply's row `syncId` as `expectedRevision` and a fresh prepare `thread`. Unknown/partial acceptance is not definite refusal. Keep already accepted recipient evidence; never silently resend the whole set.

`replies.cancel` applies to the human's own queued reply within the Undo window. Use its current row revision and restore generation. Do not promise recall after provider acceptance. `replies.discard` also needs current guards and appropriate authorship; deleting unsent content is not a delivery recovery strategy.

For an eligible held reply, `replies.release` needs the reply row revision, fresh prepare thread, current authority and sender readiness. Restored or revoked-agent holds return `needs_human` and a Pipp conversation path. Give that path to the human for in-app review, then inspect actual state. Do not release through a fresh connection, reuse pre-restore revisions or copy the body into a new send to bypass the hold.

Revocation ends future delegated access. If receipt reads are denied, follow the fresh adapter challenge or human handoff described above; a receipt ID does not confer authority, and historical errors do not justify reconnect. Ambiguous refresh failures require safe reconnect, not repeated refresh-token replay. Previously accepted provider mail cannot be recalled by disconnecting the agent.
